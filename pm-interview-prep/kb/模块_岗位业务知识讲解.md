# 模块_岗位业务知识讲解（T9 强制前置 · 五段式）

## 一、第一性原理定位（为什么必须先讲业务）

面试里所有"答得出来"的题，底下都垫着同一层东西：**你知道这个岗位在替公司解决什么问题**。

反过来，跳过这一层直接出题，会发生三件事：

1. **题目退化成押题**——脱离业务的题是从题库复制的，不是从这个岗长出来的，命中率低（违反 §9 防火墙 #1/#5）。
2. **逐字稿是从档案"推"出来的**——AI 用 kb 里的简历/方法论硬凑动机与匹配，逻辑自洽但一追问"说具体点"就穿帮（HoverAir 一面实测：动机段只能推，不能长）。
3. **业务认知题（F 维度）直接失守**——"你怎么理解这个岗""我们网站你觉得哪里能改"这一整类题，没有业务地基就是空话。

所以正确顺序是：**先讲业务 → 再定考点 → 最后出题目**。业务讲解是地基，题目是地基上长出来的结构，不是反过来。

> 一句话：**不懂业务就没有答题的地基。** 面试官每一题本质上都在验证你对这条业务链路的理解深度。

## 二、强制规则（硬约束）

| 规则 | 内容 |
|---|---|
| 触发范围 | **任何"生成面试方案"的请求**：T9 全流程、一面专项包、二面专项包、轮次专项包、临场补稿。只要产出面向某岗位的准备方案，一律适用 |
| 时序 | 排在「**普及岗位相关知识**」阶段的**最前面**——在企业速览/竞品/术语/速成包之前 |
| 截止线 | **必须在产出任何题目、任何逐字稿之前完成** |
| 省略条件 | **无**。用户没提 ≠ 不用做；篇幅紧张 ≠ 可以砍（篇幅紧只压缩案例、不压缩五段）；用户催"直接给题" ≠ 可以后置 |
| 输入来源 | 岗位 JD + 公开信息 + 企业调研（步骤 ①） + 第一性原理推导。**与步骤 ① 企业调研同步互为输入**，调研结果回来后校正一次 |
| 输出去向 | ① 进交付文档「普及岗位相关知识」章节首段；② 同步进 `索引_<公司>.md`；③ **作为后续所有题目的设计依据** |

## 三、五段式结构（每段：讲什么 / 输出格式 / 出题挂钩）

### 段 1 · 岗位为什么存在（第一性原理）

**讲什么**：公司为什么需要这个岗位？它替公司解决什么商业问题？创造了什么价值？

推导三问（必答）：
- 如果撤掉这个岗位，公司会**少赚/多花/慢多少**？（价值可量化才叫讲清）
- 公司当前处于什么阶段，才让这个岗位**此刻**有必要？（阶段决定岗位重心）
- 这个岗位买的是「人」还是「能力」？（实习生岗通常买的是可被带教的产能）

**输出格式**：
> **岗位存在的根本原因**：一句话。
> **它解决的商业问题**：1–3 条，每条配一个可感知的后果。
> **它创造的价值**：尽量落到钱/时间/风险三个口径之一。

**出题挂钩** → 对应「动机题 / 你为什么适合」「你觉得这个岗在做什么」「如果我们这个岗要砍掉，你怎么说服我留着」。

### 段 2 · 业务在链路中的位置

**讲什么**：这块业务在公司整体产品业务链路里的哪一段？上下游分别是什么？它**承接什么、交付什么**、和哪些团队/模块协作？

**输出格式**（表格最省事）：

| 上游（谁给它输入） | 本业务（做什么） | 下游（交付给谁） |
|---|---|---|
| … | … | … |

再补一行：**协作方** = 哪些团队（研发/设计/运营/市场/客服/供应链/法务合规），各自在这条链上管什么。

#### 段 2.1 · 部门业务定位（v1.2 新增 · 投前必查）

**第一性原理**：段 2 回答"业务在链路哪一段"，段 2.1 回答"**这条链路归哪个部门、这个部门替谁扛指标**"。这两件事经常不是同一条——JD 写的主题、招聘页挂的团队、面试官自我介绍的部门，三者可能互相错位。**一旦错位，按 JD 主题准备的主弹药会被整体绕过。**

**推导四问（每场必答，不许跳过）**：

| 问 | 怎么答才算答到 |
|---|---|
| ① 这个岗位所在部门在公司里解决什么 | 一句话讲清它**替谁扛什么**（不是"我们做会员"这种业务描述） |
| ② 它对什么结果负责 | 1–2 个可被考核的数字（收入 / 留存 / 转化 / 渗透率） |
| ③ **JD 写的主题与该部门的真实主线是否一致** | 一致 → 主弹药按 JD 主题挑；**不一致 → 冲突必须标出，并在反问环节澄清**（见 §五 澄清反问） |
| ④ 面试官自述的岗位，与 JD 差在哪 | 差在哪一层（团队 / 职责 / 汇报对象 / 考核口径），差得越远越要早问 |

**输出格式**（表格，标事实/推测）：
> **部门**：…（事实来源：官网 / 招聘页 / 面试官自述）
> **真实主线**：…｜**对谁负责**：…（1–2 个指标）
> **与 JD 主题的偏差**：无 / 有，偏差在 …（**有偏差则此行必须存在**）

**美图一面实证（2026-09-24）**：JD 写"会员产品方向 · 影像产品运营团队"，但面试官开场自述负责**美图商业化**，并明讲所在部门是**中台**、支撑各产品线商业化、**直接对收入目标负责**。结果 = 按 JD 主题准备的会员弹药全程未被启用，实际被挖的是字节广告变现 + 百度分润。**偏差存在却没被识别，是本场最大的可避免损失。**

> **要挖深时 → 走 `业务理解双轴模块.md` §3「内外坐标提问法」**。本段只列"谁是谁"（浅层），§3 的**对内四问**进一步要求答出"协同部门的**核心考核指标**、以及**我做什么能提升他的指标 / 他做什么能帮我**"（深层）。面试官追"你怎么和 X 协作""你的工作对谁有价值"时，浅层表格接不住，必须用 §3 的因果链。**对外三问**（竞品 / 区别 / 护城河）本段不覆盖，也去 §3。

**出题挂钩** → 对应「你怎么和 X 协作」「上下游给你数据时你怎么验」「需求冲突怎么排优先级」「研发说做不了怎么办」。

### 段 3 · 用户行为路径

**讲什么**：目标用户是谁？怎么触达？怎么用？关键行为节点与转化点在哪？

**输出格式**（漏斗式一行一个节点）：
```
触达 → 落地/首屏 → 浏览/选型 → 加购/留资 → 注册/下单 → 支付 → 履约/售后 → 复购/推荐
```
每个节点标三件事：**用户在这一步在想什么 / 最容易流失的原因 / 这一步对应什么指标**。

再补：**目标用户画像**（谁在买、谁在用，可能不是同一批人）+ **触达渠道**（付费/自然/社媒/众筹/线下/口碑）。

**出题挂钩** → 对应「你觉得我们产品/网站哪里能优化」「用户在 X 步流失你怎么查」「你怎么提升转化率」——**这一整类题的答案骨架就是这张漏斗图**。

### 段 4 · 核心业务目标与衡量指标

**讲什么**：这个岗位/这块业务的核心目标是什么？用什么指标衡量？它怎么支撑公司整体业务目标（收入/增长/留存/效率）？

**输出格式**（分层，禁止只写"提升转化率"这种空话）：

| 层级 | 目标 | 指标（可计算） | 怎么支撑公司整体目标 |
|---|---|---|---|
| 北极星/业务目标 | … | … | … |
| 过程指标（岗位日常盯的） | … | … | … |
| 护栏指标（不能为了前者牺牲） | … | … | … |

规则：每个指标必须能说出**口径 + 当前大致量级（无数据则标"待查"）+ 好坏的判断基准**。这条直接对齐 `数据口径量化标准.md` 的七要素。

#### 段 4.1 · 业务痛点（v1.2 新增 · 指标必须挂在痛点上）

**第一性原理**：孤立报一个指标没有说服力，因为面试官无法判断"这个数好不好"。**指标 + 痛点成对出现，才构成"我知道你现在难在哪"的证据。** 只列指标 = 背数字；指标挂痛点 = 懂业务。

**输出格式**（2–3 条，不超过 3 条，多了等于没重点）：

| 痛点 | 表现（现象，不是形容词） | 挂在哪个指标上 | 事实/推测 |
|---|---|---|---|
| … | … | 段 4 的哪一行指标 | 事实/推测 |

**纪律**：
- 痛点写**现象**不写形容词。"会员续费漏斗在第二级掉得最狠"是痛点；"会员运营压力较大"不是。
- 痛点**必须能挂上段 4 已有的指标**。挂不上说明这个痛点是编的，删掉。
- 从 JD 的动词与公司公开动作里反推（"我们这个岗要梳理流程"→ 痛点可能是**跨部门口径不一致**），**标推测，不当结论说**，转成反问抛回去验证。
- 查不到就写「待查/面试时问」，禁止编一个听起来合理的痛点。

**出题挂钩** → 对应「你怎么衡量你做的这件事有价值」「指标涨了你怎么判断是不是你带来的」「指标跌了你怎么拆」。

### 段 5 · 出题映射（讲解 → 题目的转换表）

**讲什么**：把上面四段逐条转成面试题目，明确"这一题考的是链路哪一环"。

**输出格式**：

| 题目 | 对应链路/行为/目标 | 考察维度（5 维） | 命中的 A–F 人设风险 |
|---|---|---|---|
| … | 段 3 加购环节 | 产品思维/数据 | F（业务了解） |

规则：**每一道出的题都必须能在这张表上找到来源**。找不到来源的题 = 从题库复制的押题，砍掉或标注"通用兜底题"。

## 四、写作风格要求

- **结构化**：表格 / 分层列表 / 一行一节点。禁止大段散文。
- **通俗易懂**：短句，主语清楚，优先日常词。专业术语第一次出现时用一句大白话解释（例：DTC = 品牌自己卖给用户，不经亚马逊这类平台）。
- **每段配「面试怎么用」**：讲完就告诉用户这段在面试里能接哪类题。只讲知识不给用途 = 用户记不住。
- **事实 / 推测分标**：公开可查的写事实，AI 推断的必须标「推测」，且尽量转成反问抛给面试官，不要当结论说。

- [ ] 段 2 有明确的上下游 + 协作方

## 六、红线

- **不编造**：公司真实数据查不到就写"待查/需面试时问"，禁止编数字冒充事实。
- **不省略**：见 §二 强制规则，无例外。
- **不后置**：题目和逐字稿必须在讲解之后产出。
- **不替代 5 问**：本模块讲**客观业务**（AI 主导）；`模块_面试前5问.md` 引导**用户主观答案**（动机/匹配/收获，必须用户口述）。两者是地基的两半，缺一不可，不可互相顶替。
- **不脑补部门与痛点**（v1.2）：段 2.1 的部门定位、段 4.1 的痛点，查不到就标「待查」并转成反问。**从岗位 JD 的字面逻辑"推"出来的部门与痛点，一律标推测**——美图一面已证明 JD 主题与实际部门可以是两条线，推错=整场主弹药作废。
